AIS-HA · IMPLEMENTATION PATTERNS

既存controlを使う。

Human Anchorのために新しいcontrol planeを発明する必要はありません。既存のidentity、authorization、policy、approval、revocation、resource、logging、recoveryへ境界を対応付けます。

実験的な実装・検証プロファイル。 この資料は、LUMINA-30の公開境界概念と関連研究から導いた実装・検証候補です。LUMINA-30正典の拡張、認証制度、安全保証、特定製品の評価・推奨を意味しません。
共通ルール： 1つのprotected authority transition、それを成立不能にできるenforcement gate、独立human authority、claimを試すevidence、そしてclaimを反証するalternate pathを明示します。

Pattern A

これらは実装例であり、特定の製品構成を必須化するものではありません。Patternの採用だけでAIS-HA PASSにはならず、PilotとVerification Matrixによるbounded evidenceが必要です。

Access escalation

例: read-only agentがwrite/admin permissionを要求。

  • approval前にauthorityが発生しない。
  • approverとrequesting agentを分離。
  • permission/resource/scope/expiryをbind。
  • rejectならgrantなし。
  • expiry/revocationをtest。
  • unregistered authorityをdeny。

Challenge: 別identity、delegated token、inherited role、recovery pathで同じaccessへ到達できないか。

Pattern B

High-impact tool execution

例: shell、deployment、transaction、external actuator。

  • tool execution前にgate。
  • denyをlogだけでなくenforce。
  • approvalを別callへreplayできない。
  • admission前はtool inactive。
  • agentがpolicy/enforcement pointを無効化できない。

Challenge: 別toolやlower-level actuatorで同等effectへ到達できないか。

Pattern C

Information egress

例: sensitive data、publication、external transmission。

  • irreversible release前にgate。
  • destination/data scopeをbind。
  • deny payloadがalternate channelから出ない。
  • stale approvalで後のpayloadを認可しない。

Challenge: logs、browser、connector、clipboard、side channel、affiliate serviceから同じ情報が出ないか。

Pattern D

Boundary mutation

例: issuer、policy、connector、approver、trust root、delegation graph、enforcement logic変更。

  • old trusted configurationが変更をauthorize。
  • 変更されたauthority-bearing componentはadmissionまでinactive。
  • new configurationがself-activateできない。
  • transfer non-VALID中はtransitively dependent protected transitionをHOLD。

Challenge: new invariant/transfer evidenceがVALIDになる前にconfiguration changeがauthorityを作れないか。

Pattern E

Restart / restoration

例: restart、failover、rollback、backup restore、credential recovery。

  • revoked authorityが復活しない。
  • restart後もHOLD維持。
  • rollbackはassumptionがcurrentなときだけVALIDを戻す。
  • validityがstale/unknownならfresh review。

Challenge: normal executionならrejectされるcredential、policy、connector、actuatorをrecovery pathが復活させないか。

UNKNOWNへ戻すべきとき

必要pathが観測できない、dependencyを確立できない、evidenceがstale/conflicting、scopeが曖昧、real authority-bearing pathのmodel gapが疑われる場合は、confidenceを創作せずUNKNOWNとします。
